# 勤務表システム デスクトップ版移行計画

## 前提

- 現行GAS版は実運用で使い続けるため、移行作業では変更しない。
- デスクトップ版は `desktop/` 配下で別系統として作る。
- まずLinux上で検証し、Windows版パッケージ化を前提に設計する。
- エンドユーザーにはローカルサーバー、ポート、solverプロセス、ログ操作を意識させない。
- GAS版で固まっている業務仕様は尊重するが、コードを直接改変して移行しない。

## 目的

現行GAS版の勤務表作成精度を保ちながら、将来的にWindowsアプリとして配布できる形へ移行する。

ユーザー体験は以下を目標にする。

- アプリを起動するだけで使える
- 職員、希望休、勤務条件を入力できる
- 勤務表を作成できる
- 作成結果の確認事項が分かりやすく表示される
- Excel/PDFで出力できる
- エラー時に「原因」と「次にすること」が分かる
- 裏側のAPI、solver、DB、ポート管理は自動で処理される

## 非対象

初期段階では以下を対象外にする。

- GAS版の改修
- GAS版とのリアルタイム同期
- Google Sheetsを直接編集する機能
- 複数PC同時編集
- クラウド共有
- 自動アップデート
- Windowsインストーラー作成

これらは試作が安定してから検討する。

## 推奨構成

```text
desktop/
  docs/          移行計画、仕様、検証記録
  core/          勤務表データ構造、判定、診断
  api/           ローカルAPI
  app/           画面
  storage/       SQLite保存
  exports/       Excel/PDF出力
  packaging/     Windows/Linux配布設定
```

実行時の構成は以下を想定する。

```text
TauriまたはローカルWeb UI
  ↓
内蔵ローカルAPI
  ↓
勤務表コア処理
  ↓
OR-Tools solver
  ↓
SQLite / Excel / PDF
```

## 段階的な進め方

### Phase 0: 保全

- GAS版を変更しない運用ルールを明文化する。
- `desktop/` 配下だけで作業する。
- 既存GASファイルを編集しない。
- GAS版から仕様を読む場合も、読み取り専用として扱う。

完了条件:

- この計画書が存在する。
- 移行作業の保存場所が `desktop/` に限定されている。

### Phase 1: データ形式の固定

デスクトップ版の最小データ形式を決める。

- 職員
- 職種
- 勤務可能シフト
- 月間夜勤回数条件
- 固定休
- 希望休
- 希望勤務
- 出張、産休、育休、休職などの供給除外
- 必要配置
- 前月末引き継ぎ
- 作成結果
- 診断結果

完了条件:

- JSONサンプルを作る。
- 既存solver入力に近い形で保存できる。
- GAS依存のセル座標を含めない。

### Phase 2: ローカルAPI試作

最低限のAPIを作る。

- `GET /health`
- `POST /schedule/solve`
- `POST /schedule/validate`
- `POST /schedule/recover`
- `POST /export/excel`

完了条件:

- Linux上でローカルAPIが起動する。初期実装済み。
- サンプルJSONから勤務表を作成できる。handler経由とHTTP経由のテスト済み。
- 診断メッセージを返せる。handler経由とHTTP経由のテスト済み。
- 同梱Linux solverをbootstrap経由で呼び出す一気通貫テスト済み。

### Phase 3: 画面試作

ブラウザで動く最小画面を作る。

- 職員一覧
- 希望休入力
- 勤務表表示
- 作成ボタン
- 診断表示
- Excel出力ボタン

完了条件:

- 診断表示用ViewModelで「結果」「確認事項」「修正が必要」「不足」「希望未充足」「対応候補」の表示順を固定する。初期実装済み。
- 勤務表表示用ViewModelで職員数と月日数に動的追従する。初期実装済み。
- アプリ表示用ViewModelで作成前後のボタン状態と診断状態を管理する。初期実装済み。
- HTMLレンダラとプレビューサーバーでブラウザ確認できる最小画面を表示する。初期実装済み。
- 画面からローカルAPIへ入力確認・勤務表作成を呼ぶクライアント/コントローラ層を固定する。初期実装済み。
- Excel/PDF出力へ渡す共通Workbookモデルと、プレビュー用XLSX出力を作る。初期実装済み。
- `POST /export/excel` で出力先へXLSXを書き出す正式API経路を作る。初期実装済み。
- PDF出力へ向けた印刷用HTML、Chrome PDF runtime、`POST /export/pdf` の正式API経路を作る。初期実装済み。
- ユーザーがコマンドを触らずに、画面上の操作だけで一連の流れを確認できる。
- 診断表示は「結果」「確認事項」「不足」「希望未充足」「対応候補」の順で表示する。

### Phase 4: アプリ化

ローカルWeb UIをTauriで包む。

- アプリ起動時にAPIを自動起動
- 空きポートを自動選択
- `127.0.0.1` のみにbind
- API停止時の自動再起動
- アプリ終了時の子プロセス終了
- ログ保存

完了条件:

- アプリruntime層でAPIを自動起動し、空きポートを使い、`127.0.0.1` のみにbindする。初期実装済み。
- runtime層で停止、再起動、起動失敗状態を扱う。初期実装済み。
- runtime-backed app shellで画面操作を内部APIへ接続する。初期実装済み。
- app shellから保存、読込、バックアップを操作できる。初期実装済み。
- app shellからJSONデータの確認、反映、出力ができる。初期実装済み。
- app shellから勤務表TSVの確認、反映、出力ができる。初期実装済み。
- Linux launcherでapp shell起動とブラウザ起動を自動化する。初期実装済み。
- Linux developer launcher wrapperとdesktop entry生成を用意する。初期実装済み。
- Windows launcherでapp shell起動とブラウザ起動を自動化する。初期実装済み。
- Linux上で通常アプリとして起動できる。
- ユーザーがローカルサーバーを意識しない。

### Phase 5: Windows配布検証

Windows版に必要な項目を検証する。

- インストーラー
- OR-Tools同梱
- SQLite保存先
- Excel/PDF出力
- Windows Defenderの警告
- ログ収集
- バックアップ復元

完了条件:

- Linux試作版とWindows試作版のリリース準備判定を同じmanifestで確認できる。初期実装済み。
- Linux試作版は同梱solver、launcher、desktop entry計画が揃っていることを自動判定できる。初期実装済み。
- Windows試作版はWindows launcherとWindows用solverを必須として判定する。初期実装済み。
- Windows用solverのPyInstallerコマンドを同じbuild planから出力できる。初期実装済み。
- 現在OSを自動判定して、必要なsolver同梱物をビルドし、readinessまで確認する入口を用意する。初期実装済み。
- 配布準備の上位入口で、solver準備とreadiness確認をまとめて実行できる。初期実装済み。
- 配布物の組み立て入口で、準備済みファイルを `desktop/` 外の出力先へ集められる。初期実装済み。
- 組み立て後の成果物を起動し、初期画面、入力確認、勤務表作成経路を自動smoke確認できる。初期実装済み。
- smoke済み成果物をアーカイブ化し、チェックサムとmanifestを出力できる。初期実装済み。
- アーカイブを別フォルダへ展開し、展開後の成果物も自動smoke確認できる。初期実装済み。
- Windows試作版はWindows用solverが未同梱なら未準備として止まる。
- Windowsでアプリ起動から勤務表作成まで確認できる。
- ユーザーがコマンド操作なしで使える。

## エンドユーザー向け表示方針

内部用語は通常表示しない。

避ける表現:

- hard
- infeasible
- solver
- acceptable_with_advisory
- deploymentReadiness
- shortageDiagnostics

使う表現:

- 作成できました
- 作成を止めました
- 確認事項
- 修正が必要
- 許容内の不足
- 休暇未充足
- 勤務希望未充足
- 対応候補

表示順:

1. 結果
2. 確認事項
3. 修正必須
4. 不足
5. 希望未充足
6. 対応候補

## ローカルアプリ運用方針

ユーザーに任せないもの:

- API起動
- ポート選択
- solver起動
- DB初期化
- ログ保存
- バックアップ
- エラー詳細の技術ログ確認

ユーザーが操作するもの:

- 職員登録
- 希望休入力
- 勤務表作成
- 手修正
- 再判定
- Excel/PDF出力
- バックアップ復元

## 最初の技術検証

最初に作るもの:

- `desktop/core` のデータ型定義
- `desktop/api` の `/health`
- サンプル入力JSON
- solver呼び出しの薄いラッパー
- 結果メッセージ整形関数

最初はUIを作り込みすぎない。

目標:

```text
サンプルJSONを読み込む
勤務表を作成する
結果と確認事項をJSONで返す
Excel相当の表形式に変換する
```

## 保留事項

- Tauriにするか、まずローカルWebのみで進めるか
- APIをPython FastAPIにするか、Nodeにするか
- solverを既存 `solver_cli` 参照にするか、`desktop/solver` に複製するか
- Excel出力ライブラリ
- PDF出力方式
- SQLiteスキーマ
- Windows署名

## 作業ルール

- GAS版ファイルは変更しない。
- GAS版の修正が必要に見えても、まずユーザーに確認する。
- 移行用ファイルは `desktop/` 配下に置く。
- 仕様判断はこの計画書に追記してから実装する。
- 実装後はGAS版ではなく、desktop側のテストで検証する。
